# mock-review: independent, verifiable mock review

## The problem this skill addresses

The most common failures of mock review (item 7 of `FAILURE_MODES.md`):
1. **Not independent.** The reviewing subagent has read the author's notes, revision plan, or earlier reviews, so it follows the author's line of thought and cannot find problems the author did not think of.
2. **Not verified.** "Errors" claimed by a subagent are adopted directly. In fact, it may have misread, and its numbers may be inaccurate.
3. **Line-number drift.** The manuscript version used at review time was not recorded, so by revision time the line numbers no longer match.

The author's own practice in Case B serves as a model (see paper-polish's `references/case-studies.md`):
- three reviewer roles reviewed independently, then held a cross-discussion, with the first-round text preserved;
- the manuscript was pinned by SHA-256;
- another mock reviewer did not read the joint report and reproduced all the numbers in a copy under `/tmp`;
- the main session recomputed, one by one, the errors it raised: most were fully confirmed; one was only substantively confirmed, with details needing correction.

## Hard rules

1. **Isolation.** Reviewers read only the copy generated by `review_pack.py`, not the source repository, `polish/`, notes, earlier reviews, or the cover letter. Only the editor role may read the cover letter, and only when the main session explicitly provides it.
2. **Version pin.** Line numbers in reports are valid only for the hash recorded in `PIN.json`. Before revising according to review comments, run `check-pin` first.
3. **Reproduce in each reviewer's own copy** (`work-<role>/`); touch neither the pack nor the source repository. If a server or long computation is needed, ask the user first. Subagents do not install software: a check that needs a missing package is reported as not checked, and installing it is the user's decision.
4. **Adopt only after verification.** The main session must re-check every claimed "error": recompute, read the source code, or read the original source. Conclusions are confirmed / refuted / partially confirmed; nothing unverified enters P0.
5. **Label it as simulated.** State at the top of the report: "This report was generated by AI mock review and does not represent the decision of real reviewers or the journal." Do not send it to anyone or submit it in any way.
6. Put all outputs outside the repository: `~/mock_review/<repo>-<YYYY-MM-DD>/`, or a directory the user specifies. The final report may be copied back into a directory inside the repository that has been added to `.git/info/exclude`.
7. Talk to the user and write reports in the user's language. If the user prefers, the review reports may instead follow the target journal's reviewing language, which is more realistic; the default is the user's language.

## Modes

- **Full** (default): Phases 0–7 below, 2–4 reviewer roles, cross-discussion and a joint report. Use it before submission and after a rejection.
- **Quick** (`--quick`): a kill-argument round, minutes instead of hours. Use it while the paper is still changing, to test a new framing, or to decide whether a full round is worth it. Steps:
  1. **Pack and pin** as in Phase 1.
  2. **Attack.** One fresh subagent, isolated as in rule 1, writes the strongest rejection memo it can, at most 200 words and at most 3 kill arguments, each with a location and evidence (prompt in Section 6.1 of `references/templates.md`).
  3. **Defend.** Another fresh subagent, which sees the memo and the recomputations the attacker listed but none of its other reasoning, answers each argument with REBUTTED (quoting the paper), FIXABLE (with the minimal change) or STANDS (Section 6.2).
  4. **Verify.** The main session checks every argument that was not cleanly rebutted, and every rebuttal it doubts, as in Phase 5, including the innocent explanations.
  5. **Report.** Write `quick_report.md` (Section 6.3): each kill argument, the defense, the verification, the status, and the next step. A rebutted argument still means the answer is not visible enough to a referee.

  Quick mode does not replace a full review: it looks for reasons to reject, not for every problem. A run on a real manuscript is summarized in `examples/README.md` at the repository root.

## Phase 0: Intake

- The manuscript directory (a git repository or a plain folder) and the entry files (main manuscript and supplementary material; LaTeX, Word, or PDF). If there is only a single Word manuscript, put it and the supplementary material in a new folder before packing.
- The target journal. Fetch the journal's official reviewer criteria page, excerpt it verbatim, and save it as `criteria.txt`.
- The purpose of the review, which determines the emphasis:
  - pre-submission self-check: comprehensive;
  - post-rejection diagnosis: focus on the reasons for rejection;
  - before responding to reviewer comments: simulate whether the same reviewer can be persuaded.
- Budget: the number of reviewer roles (default 3), and whether to add the editor role.

## Phase 1: Pack and pin

```
python3 <skill-dir>/scripts/review_pack.py pack --repo <repo> --out ~/mock_review/<name>-<date> --roles <r1>,<r2>,<r3>
```

- Read `MANIFEST.md` and check the section "Copied files whose names look like author notes".
  - Reviews, revision plans, and author notes about **this manuscript itself**: exclude them with `--exclude` and repack into a new directory.
  - Notes in a public repository that already serve as part of the research record: may be kept, since real reviewers can see them too; when unsure, ask the user.
- Note the manuscript hashes recorded in `PIN.json`.

## Phase 2: Choose reviewer roles

Choose 2–4 roles by paper type and components; each role corresponds to a type of real reviewer. The menu of roles for each paper type and the corresponding reporting guidelines are in Section 5 of `references/templates.md`. Common combinations:
- theory + application: mathematical proofs, application domain, methodology;
- experimental or clinical studies: domain expert, statistics and study design, reporting guidelines and ethics (CONSORT, ARRIVE, etc.);
- observational studies: domain expert, epidemiological or causal-inference methods, statistics (STROBE, etc.);
- computational or machine learning: domain expert, methods and fairness of baselines, reproducibility (code, data, seeds, data leakage);
- qualitative research: domain expert, qualitative methods (SRQR, COREQ);
- systematic reviews or meta-analyses: domain expert, methodology and risk of bias (PRISMA, GRADE);
- optional editor role: reads only the title, abstract, introduction, Figure 1, and cover letter, and decides whether to send the paper out for review (paper-polish's `references/blind-editor-test.md` can be reused).

Write a one-sentence responsibility statement for each role, for example:
- "You are a scholar in analytic number theory; focus on checking the counting proofs in the appendix";
- "You are a clinical trial statistician; focus on checking the sample size calculation, the primary endpoint analysis, the handling of missing data, and compliance with CONSORT".

For roles involving reporting guidelines, the main session first fetches the verbatim text of the guideline's official checklist (from the EQUATOR Network or the guideline's official website) and gives it to the reviewing subagent to check item by item.

## Phase 3: Independent review (in parallel)

**Optional cross-model reviewer.** Reviewers from one model family share blind spots. If the user has another model available, one role can run there with the same pack and prompt (Section 7 of `references/templates.md`). Sending an unpublished manuscript to another provider shares it with that provider: ask the user first, every time, and name the provider.


Launch one subagent per role in a single message; the prompt template is in Section 1 of `references/templates.md`. Requirements:
- read only `pack/`; run code only in `work-<role>/`;
- write the report to `reports/<role>.md`, structured according to the template:
  1. Summary;
  2. Recommendation and confidence;
  3. Strengths and weaknesses (against the journal criteria);
  4. Major issues, each stating location, evidence, and requested change;
  5. Minor issues;
  6. Verification performed (which files were read, which commands were run, which numbers were reproduced);
  7. Parts not checked.
- list all files read at the end of the report, to check whether isolation was broken.

## Phase 4: Cross-discussion

- Use SendMessage to send the other reviewers' reports to each reviewing subagent (they retain their original context). Ask each to **append** a "Cross notes" section at the end of its own report: what it agrees with, what it disagrees with (with reasons), and which of its own points it withdraws or escalates. **The first-round body must not be modified.**
- If a subagent has already finished and cannot continue, start a new subagent and give it both the original report and the other reports; again, only appending is allowed.

## Phase 5: Verification by the main session

For all major issues, especially those of the "error" type:
1. In the main session's own copy (e.g. `work-main/`, or a fresh `cp -R`), recompute, read the source code, and read the cited sources.
2. Record in `verification.md`:

| # | Source reviewer | Claimed issue | Verification action (command or file) | Result | Basis |
|---|---|---|---|---|---|

3. The result is one of three: confirmed / refuted / partially confirmed (state which part is confirmed). For numerical issues, give the recomputed value.
4. **Before confirming, rule out the innocent explanations** and record which ones were checked: a convention or definition stated elsewhere in the paper, material in the supplement, a different but equivalent formulation, a reviewer misreading, or a difference between the pinned version and the one the reviewer quoted. An issue that survives these is confirmed; one that depends on them is refuted or partially confirmed.

## Phase 6: Joint report

Write `joint_report.md`; the template is in Section 2 of `references/templates.md`. Key points:
- At the top, state that this is a mock review, the pinned hash, and that "line numbers apply only to this version".
- **Overall assessment table**: one row per role, giving the independent assessment, main points endorsed, and main revision requests.
- **Priority revision table**:

  | Priority | Issue and evidence | Scope of verdict | Minimal fix |
  |---|---|---|---|

  - P0: if left unfixed, the paper's claims are inconsistent, or it is a verified factual error;
  - P1: affects readers' ability to use or verify the results correctly;
  - enhancements.

  Only issues verified as confirmed may enter P0.
- **Separate wording issues from substantive issues.** Mark substantive issues as "requires new results".
- **Revision order**: A, B, C, …; state the completion criterion for each step.
- **Verification record**: what was actually done in this round, what was not done (e.g. "Appendices G–J were not checked lemma by lemma"), and the reproduction commands.
- Present disagreements between reviewers as they are; do not force a unified position.

## Phase 7: Follow-up

After the user revises according to the report, you can:
- run `review_pack.py check-pin <PIN.json>` to see which line numbers are no longer valid;
- run another round with **new** subagents. The old subagents have already seen the previous version and their own conclusions, so they are no longer independent.

## Final report to the user (concise, in the user's language)

- The independent recommendation of each role, one sentence per role.
- The P0 issues verified as confirmed (count, one sentence each), and the claimed errors that were refuted.
- The 1–3 things to do first.
- The path to the report directory; restate that this is a mock review.
