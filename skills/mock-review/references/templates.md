# Templates

## 1. Reviewer subagent prompt

```
You are an independent referee for <journal>, expert in <direction>. Your
specific responsibility: <one sentence, e.g. "verify the number-theoretic
proofs in Appendices F-J and the tube-count constants">.

Materials (read-only): <pack path>. The manuscript is <main.tex, supplement.tex>,
version pinned by SHA-256 in <PIN.json>; your line numbers refer to this version.
Journal criteria (verbatim): <criteria.txt>

Rules:
- Read only inside <pack path>. Do not open any other directory, in particular
  not the source repository, author notes, earlier reviews or cover letters.
- Run code only in your work copy <work-role path>. Record every command. Do not install
  software; if a check needs a missing package, report it as not checked.
- Reproduce numbers where you can; say which you reproduced and which you did not.
- Be concrete: every major issue needs a location (file:line or theorem/figure),
  the evidence, and the change you request.
- Do not soften or inflate: state your confidence for each part.

Write your report to <reports/role.md> in <language> with these sections:
1. Summary of the submission (what is claimed, in your own words)
2. Recommendation and confidence (accept / minor / major / reject / transfer;
   confidence per part: high / moderate / low)
3. Overall assessment: strengths; weaknesses relative to the journal criteria
4. Major issues (M1, M2, ...): claim, location, evidence, requested change
5. Minor issues (numbered)
6. Verification performed (files read, commands run, numbers reproduced with values)
7. Not checked (be explicit)
8. Files read (complete list)
```

## 2. Joint report structure (`joint_report.md`)

```markdown
# <number of roles>-role joint review and revision plan

Date: YYYY-MM-DD. This report was generated by AI mock review and does not represent the decision of real reviewers or the journal.
Version pin: main.tex SHA-256 `...`; supplement.tex `...`. Line numbers apply only to this version.

## 1. Overall assessment

<One paragraph: the recommended conclusion; what most needs fixing; what was not overturned; what has not yet been independently certified>

| Reviewer role | Independent assessment | Main points endorsed | Main revision requests |
|---|---|---|---|

<Differences in emphasis across roles; consensus and disagreements after cross-discussion>

## 2. Priority issues and their nature

| Priority | Issue and evidence | Scope of verdict | Minimal fix |
|---|---|---|---|
| P0 | ... | Verified factual error / claim exceeds what has been proven / ... | ... |

"P0" means it must be fixed first for the paper's claims to be consistent; it does not necessarily mean the core theorem is wrong. "P1" should not be treated as mere copy-editing either.

## 3. Recommendations for specific issues
<Issue by issue: definitional text that can be adopted directly, minimal verifiable examples, proof steps that need to be added>

## 4. Concrete improvements obtained in this round (if any)
<e.g. tighter numerical bounds, proofs filled in, with recomputation scripts>

## 5. Revision order

| Order | Change | Completion criterion |
|---|---|---|

## 6. Verification record and follow-up work

Actually completed in this round: ...
Not completed in this round: ... (must not be written as "verified")
Recomputation commands: ...
- [ ] Check the manuscript hash before continuing revisions (`review_pack.py check-pin`)
- [ ] ...
```

## 3. Verification record (`verification.md`)

```markdown
| # | Source | Claimed issue | Verification action | Result | Basis |
|---|---|---|---|---|---|
| 1 | methods M2 | The tool's precision parameter uses a different distance | Read the source code of the pinned version; use the repository data to compute "measured error ÷ nominal parameter" | Confirmed | Source code location; ratio about 0.5 |
| 2 | stats minor 1 | "Other parameters give at most X" is incorrect | Parameter sweep in the copy | Confirmed | Sweep output; maximum exceeds X |
| 3 | theory M5 | The lower limit of a certain constant should be higher | Exact recount | Partially confirmed | The count at the parameters given by the reviewer was wrong; the conclusion is substantively confirmed |
```

## 4. Editor role (optional)

Use Section 2 of paper-polish's `references/blind-editor-test.md` directly, giving the editor only the title, abstract, introduction, Figure 1 caption, and (optionally) the cover letter. Put the editor's conclusion in a separate section; do not merge it with the reviewers' recommendations.

## 5. Reviewer role menu and reporting guidelines

Pick 2–4 roles by paper type. Fetch reporting guideline checklists verbatim from official sources (EQUATOR Network: equator-network.org, or each guideline's official website); do not list items from memory.

| Paper type | Candidate reviewer roles | Common reporting guidelines |
|---|---|---|
| Theory / mathematics | Correctness of proofs; relation to existing results; significance for applications | — |
| Randomized controlled trials | Clinical or domain expert; trial statistics (sample size, primary endpoint, multiplicity, missing data); ethics and registration | CONSORT (including the extension for abstracts), SPIRIT (protocols) |
| Observational studies | Domain expert; epidemiology and causal inference (confounding, selection bias, sensitivity analysis); statistics | STROBE, RECORD (routinely collected data), RECORD-PE |
| Diagnostic accuracy | Clinical expert; diagnostic methodology | STARD |
| Prediction models | Domain expert; modeling and validation (calibration, external validation, overfitting) | TRIPOD (including TRIPOD+AI) |
| Animal experiments | Domain expert; experimental design and statistics (randomization, blinding, sample size) | ARRIVE |
| Systematic reviews / meta-analyses | Domain expert; search and risk of bias; statistical pooling and heterogeneity | PRISMA, GRADE |
| Health economic evaluations | Health economics methods; domain expert | CHEERS |
| Qualitative research | Domain expert; qualitative methods (sampling, saturation, reflexivity) | SRQR, COREQ |
| Psychology / behavioral science | Domain expert; statistics and replicability (preregistration, power, multiple comparisons) | APA JARS |
| Computational / machine learning | Domain expert; methods and fairness of baselines; reproducibility (code, data, seeds, data leakage, compute budget) | The target venue's paper checklist (e.g. NeurIPS paper checklist), REFORMS |
| Computational simulation / numerical methods | Domain expert; numerical methods and error; reproducibility | — |

In the reviewing subagent's responsibility statement, write "Check item by item against the <guideline> checklist (attached below), and flag missing items and where in the manuscript they should appear".

## 6. Quick mode: kill memo and defense

### 6.1 Attacker prompt (fresh subagent)

```
You are the most demanding referee <journal> could choose for this paper, expert
in <direction>. Your task is to find the strongest reasons to reject it.

Materials (read-only): <pack path>, version pinned in <PIN.json>.
Journal criteria (verbatim): <criteria.txt>
Read only inside <pack path>, plus <criteria.txt> and <PIN.json>. Do not open any
other directory. Run code only in <work-attacker path>. Do not install software; if a check
needs a package that is not installed, say so instead.

Write a rejection memo of at most 200 words to <reports/kill_memo.md> in <language>:
- At most 3 kill arguments (K1, K2, K3), strongest first. A kill argument is a reason
  that, if true, would make an editor reject the paper even after revision: the
  main claim does not follow, is already known, is wrong, is untestable, or does
  not matter for this venue.
- Each argument: one sentence of claim, the location (file:line, theorem, figure,
  table), and the evidence. Name the prior work if the argument is "already known".
- No style, wording or minor issues. No softening. If you cannot find a real kill
  argument, say so; do not invent one.

After the memo, list the files you read and any numbers you recomputed.
```

### 6.2 Defender prompt (another fresh subagent)

```
You are a co-author defending this paper against a referee's rejection memo. You
were not involved in writing it, and you may use only the paper itself.

Materials (read-only): <pack path>, version pinned in <PIN.json>.
Rejection memo: <reports/kill_memo.md> (the memo and the referee's listed
recomputations, which are evidence you may check)
Read only inside <pack path>, the memo and <PIN.json>. Do not open any other
directory. Run code only in <work-defender path>. Do not install software; if a check
needs a package that is not installed, say so instead.

For each kill argument, write to <reports/defense.md> in <language>:
- Verdict: REBUTTED (the paper already answers it: quote the passage and give its
  location), FIXABLE (true, but a stated change to the text or a stated additional
  analysis would answer it), or STANDS (true, and not fixable within this paper).
- Evidence for the verdict. "The authors would argue" is not evidence; quote the
  paper or recompute.
- For FIXABLE: the minimal change, and whether it needs new results.
- If an argument bundles several claims, give a verdict for each sub-claim.
Concede when the argument is right. A wrong rebuttal is worse than a concession.
End with the files you read and the commands you ran.
```

### 6.3 Quick report (`quick_report.md`)

```markdown
> AI mock review, quick mode. Not the decision of real reviewers or the journal.
> Pinned version: <hash>. Line numbers apply only to this version.

| # | Kill argument (short) | Defense | Main-session check | Status | Next step |
|---|---|---|---|---|---|
| K1 | ... | REBUTTED, quote at file:line | read file:line, the passage answers it | rebutted | make the passage visible in the introduction |
| K2 | ... | FIXABLE: add baseline X | recomputed; gap is real | stands until fixed | run X (needs new results) |
| K3 | ... | STANDS | prior work Y, Theorem 2, already proves it | confirmed | reposition; see novelty-audit |

Innocent explanations ruled out (for every confirmed kill argument): ...
Suggested follow-up: full review with roles <...> / novelty-audit / proof-audit / none.
```

A rebutted argument is still a signal. If a referee could raise it after reading the paper, the answer is not visible enough; the fix is often a sentence in the abstract or introduction.

## 7. Cross-model reviewer (optional)

Reviewers from the same model family share blind spots. If the user has another model available locally (a different assistant CLI, or a model the user runs), one reviewer role can be run there with the same pack and the same prompt (Section 1 or 6.1), and its report goes into `reports/` like the others.

Rules:
- **Sending an unpublished manuscript to another provider shares it with that provider.** Ask the user before doing so, every time, and name the provider. Never do it for a manuscript under embargo or confidentiality terms.
- The cross-model report is verified by the main session like any other (Phase 5). Disagreement between model families is reported as it is, not resolved by majority.
- Record the model name and version in the report header.
